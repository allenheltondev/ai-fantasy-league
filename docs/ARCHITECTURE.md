# Architecture

This is the contract every work stream builds against. The product is described in `docs/SPEC.md`, and the resolved decisions are in its §10. If code and this document disagree, fix one of them in the same PR.

## Stack

- **Language:** TypeScript everywhere. Node 22, ESM, `strict` mode, no `any` (use `unknown` and narrow). Validation is done with `zod`.
- **Monorepo:** npm workspaces, one lockfile at the root.
- **Backend:** AWS SAM (`infra/template.yaml`) in us-east-1:
  - Lambda (arm64, Node 22) and API Gateway-free routing: CloudFront `/api/*` → Lambda Function URL, the same pattern as llm-eval-harness. The SPA bucket is private behind CloudFront OAC. The Function URL is `AuthType NONE`, because OAC for Function URLs needs the viewer to send a body hash on POST/PUT, which browsers can't do. Instead CloudFront sends an `X-Origin-Verify` secret header to that origin and the API refuses (403) any request without it, before auth runs; the secret lives in SSM at `/<stack>/origin-verify/{current,previous}` (created by `make deploy-backend`, rotated with `make rotate-origin-secret`, both values accepted during a rotation). The local dev server has no such check. The API verifies the Cognito ID token on every route except health and OpenAPI.
  - The SPA learns its Cognito app client at runtime from `/auth-config.json`, which `make deploy-frontend` writes from the stack outputs.
  - DynamoDB for data, EventBridge (the default bus shared with rsc-core), EventBridge Scheduler for recurring jobs, and the rsc-core deferred-event scheduler for timed events. The weekly cycle is clock-driven jobs plus deferred events rather than Step Functions (`docs/adr/002-weekly-cycle.md`).
  - **Failures (#130):** every asynchronously invoked function (the EventBridge rule handlers and the data jobs) has a Lambda OnFailure destination on the default bus. An invocation that still fails after Lambda's two retries becomes `Lambda Function Invocation Result - Failure`, and `FailureNotifierFunction` (`packages/server/src/failures/`) emails it, with the failed event, to `AlarmEmail` through rsc-core's `Send Email`. League jobs finish every league, then throw if any failed (`settle` in `packages/server/src/jobs/deps.ts`), so partial failures are retried and emailed too; a league that stays broken sends one email per run. CloudWatch alarms, error-log metric filters, and SQS dead-letter queues wait until the deploy role allows them (#129).
- **Frontend:** a Vite + React 19 SPA in `app/`, served from S3 + CloudFront at `fantasy.readysetcloud.io` (Staging uses the CloudFront domain). It uses `@readysetcloud/ui` for components, tokens, the Tailwind preset, and auth (`@readysetcloud/ui/auth`).
- **Identity:** the shared rsc-core Cognito pool (`/readysetcloud/auth/user-pool-id` from SSM). This stack creates its own app client in that pool. The API verifies ID tokens with `aws-jwt-verify`.
- **Realtime:** Momento Topics, using the API key from the rsc-core secrets SSM parameter. The API vends short-lived, scoped tokens to browsers.
  - **Settings:** the key is the `momento` field of the rsc-core secret (`/readysetcloud/secrets` names it), and the cache is rsc-core's default cache (`/readysetcloud/cache-name`). Realtime is on only when both are configured (`packages/server/src/realtime/config.ts`); otherwise the no-op implementation is used, and nothing in local dev, tests, or CI needs Momento credentials.
  - **Topics:** `fantasy.league.<leagueId>` carries a league's chat messages and events, `fantasy.team.<leagueId>.<teamId>` (`teamTopic`) carries what only that team may see (its waiver awards and failed claims, its new notification inbox items, and trade offers, counters, rejections, and expiries it is part of, which never go to the league topic), and `fantasy.global` carries events with no league (the live-stats job's `Scores Updated`, and `NFL Games Updated`). Items are JSON: `{ type: 'chat', leagueId, message }` or `{ type: 'event', detailType, eventId, time, leagueId, detail }`, with the event detail passed through unchanged.
  - **Tokens:** `get_realtime_token` (people only) returns a disposable token that can only subscribe to the league topic, the caller's own team topic (when they hold a seat), and the global topic, for 30 minutes. When realtime is off it returns `enabled: false`, and the app polls `get_chat` every `pollIntervalSeconds`.
  - **Publisher:** `RealtimePublisherFunction` (`realtime/relay.ts`) relays league events from the bus to the topics. It is the only function besides the API that reads the Momento key.
- **Agents:** `@readysetcloud/agent` runs Strands on Bedrock. Agents call the league **only** through the operation registry (below) with their own principal.
  - **Flow:** league events → the trigger router Lambda (`packages/agents/src/router.ts`) → `Agent Action Requested` → the agent task Lambda (`packages/agents/src/runner.ts`). The router Lambda and the in-process loop (dev server, e2e, the season simulator) ingest events through one function, `ingestLeagueEvent` (`packages/agents/src/ingest.ts`, #211): memory first, then routing, over the union of trigger and memory-only events (`INGESTED_EVENTS`, which the router's EventBridge rule lists exactly). A failed memory write is logged and never blocks routing; both halves are idempotent on redelivery.
  - **Response delays (#189):** agents do not react the instant an event lands. The router gives each task a human-like wait from core `responseDelay` (`packages/core/src/agents/response-delay.ts`) and schedules it through the existing deferred-event path (`dispatchTask` → `events.scheduleAt`, named by the task id, at the time fixed when the task was reserved, so a redelivered trigger neither moves nor doubles it). A roll of the difficulty's `responseDelay.immediateChance` answers at once; otherwise the delay is a right-skewed (log-normal) sample around the event class's median, times the tier's `responseDelay.multiplier`, and capped. Chat (mentions, moments, banter) is not delayed: agents answer at once, paced by the chat cooldowns and budgets. Classes: trade (Trade Proposed/Countered: 45m, 8h), roster (Waiver Window Opened, Player News Alert, Player Status Changed, Week Rolled Over, Manager Check-In: 90m, 12h), deadline (Draft Turn Started: a few seconds of think time), and post_draft (jitter on top of the kickoff stagger). The delay is clamped to a share of the time left before the event's deadline: half the time before a trade's `expiresAt`, the waiver run (`closesAt`), the next check-in (`nextAt`), or the next lineup lock (player news and status, check-ins), and 40% of the pick clock, so a delayed agent never misses it. Lineup Lock Approaching and Trade Accepted never wait. The roll is seeded by event and team, so a replay gets the same delay, and the routing decision logs `delayMs`. Cooldowns are checked and spent at route time; the task re-reads the league when it runs, so a stale one is a no-op (`offer_closed` for a withdrawn, expired, or answered offer; `already_answered` for a message the agent answered; the draft task's "not on the clock"). Tiers run from rookie (×2, 5% immediate) to Hall of Famer (×0.5, 25%), and the Advanced drawer can override either field. Delays are on in the router Lambda (`AGENT_RESPONSE_DELAYS`, on unless `off`) and off in the in-process loop (`inProcessAgentDeps`), so the dev server, e2e, and the season simulator stay immediate. Quiet hours (no trade answers at 3am) are a later follow-up.
  - **Post-draft kickoff (#175):** when the draft completes, the router schedules one `post_draft` task per agent team (a minute after the last pick, then 45 seconds apart; `POST_DRAFT_KICKOFF`), once per draft. The task sets the optimizer lineup, posts one draft reaction in the league chat (the one model call: its grade by ADP value, a steal, a rival's reach, managers by name, under the chat budgets and banter guards), and claims a healthy player for each roster hole (core `rosterHoles`). High trade-appetite archetypes then take one early trade look: the task hands `trade_proposal` a follow-up (`TaskOutcome.followUps`, at most one offer). With the kill switch on or the budget spent, only the lineup and the hole claims run.
  - **Manager check-ins (#195):** agents do not only react. At 09:00, 14:00, and 20:00 US Eastern (an EventBridge schedule with `ScheduleExpressionTimezone`; core `checkInMoment`), the `managerCheckIns` job publishes one `Manager Check-In` per drafted, unfinished league with agent seats (none while the kill switch is on), and the router gives every agent a `check_in` task: once per league, date, and slot, its own cooldown slot, a roster-class delay clamped to half the time before the next check-in and the next lineup lock. The task (`packages/agents/src/tasks/check-in.ts`) first looks without a model: starters out or on bye, pickups (trending and top-ranked free agents projected against the weakest player by the archetype's `waiverMinGain`, plus roster holes), a trade look when the archetype's appetite roll passes (`checkInTradeChance`) with offers left this week (`proposalsPerWeek`, shared with the rollover look; win-win and never the same offer twice), and offers waiting on an answer. Each probe (`CHECK_IN_PROBES`) turns part of that into a reason; with none, the task is recorded as skipped `nothing_to_do` with a one-line reason and no model call. Otherwise one decision-tier call answers with a list of typed actions (`set_lineup`, `add_drop`, `claim`, `propose_trade`, `none`) picked from the vetted lists, within `actionsPerTrigger`. The fallback (kill switch, budget) sets the optimizer lineup and fills holes. An offer that has waited two hours goes to `trade_response` as a follow-up. An agent that never had a post-draft kickoff or a check-in gets `firstLook` (the kickoff's steps).
  - **Team names (#194):** AI managers name their own teams. A team records who set its name (`nameSetBy`: `owner`, `commissioner`, `agent`, or `default`) and its last renames (`renames`, shown as `renamedFrom` and as `team_renamed` entries on the dashboard's move board). `rename_team` holds an agent's name to core `teamNameIssue` (3-30 characters, not a placeholder like "Team 3" per `isGenericTeamName`, a slur/profanity blocklist, unique, no other manager's name) and refuses a name the commissioner locked. A seat's `namesTeam` (on by default, commissioner only) lets its manager name the team; with it on, the commissioner's rename goes back to `default`, otherwise it is locked. The naming step runs inside the post-draft kickoff's one model call (`rename_team` bound with one retry, the reaction opens with the new name), and as its own `team_identity` task (chat tier) on `Member Left`, `Agent Seat Changed`, and the rollover (a safety net for placeholder names, plus a rare in-character rebrand after a 3-game losing streak, a clinched playoff spot, or at the trade deadline, rolled from the personality's `rebrandPropensity`, at most once in 4 weeks, never in the playoffs). Each personality has a `namingStyle` and a few `teamNameIdeas` for the prompt; the fake model picks from them. A rename by a person gets a chat line (`Team Renamed`); an agent announces its own in character.
  - **Social check-ins and chat that changes minds (#196):** each personality has a `chattiness` and a `persuadability` (0-1; `packages/core/src/agents/social.ts` holds the rules, and the persona prompt reads them as its temperament). A check-in (`tasks/check-in-social.ts`, through the check-in's probes, actions, and steps, in the same one decision) may also rename the team (the router sets `naming` when the name is generic, at any check-in, so a league drafted before #194 is named without waiting for the rollover, or on a rebrand roll worth a twenty-first of the weekly propensity; #194's rules and its once-a-day `NAMING_COOLDOWN` apply), post once on a league board about news that concerns the agent (its streak and place, last week's blowouts and top score, a fresh trade; `checkInChatChance`), talk in its matchup room about the projections gap, the opponent's starters who will not play, a live lead, or a comeback (tagging the opponent; one per check-in, `matchupPostsPerWeek` a week), and send a DM tied to a goal (a trade to pitch, an offer a day old, an offer just turned down), never to an open seat: one agent-started thread per team per day and none while the last went unanswered unless an offer changed (`dmVerdict`). It never posts twice in a row in a room until someone else speaks, and the chat budgets and banter guards apply to everything it says. From chat to action: a `chat_reply` may mark a `takeaway` (a trade, a player tip, a taunt), which becomes one follow-up task (`TaskOutcome.followUps`, `chatDriven`, held to `chatActionsPerDay` per agent by the runner): `trade_response` for that team's open offer, `trade_proposal` (`reason: chat`) for the players named (recorded first as a commitment that takes the day's use itself; see Durable agent commitments), `lineup` for a tip that one of its players is out, `waivers` for a breakout tip or a position taunt. The follow-up re-reads the message and never shows it to its model; claims are verified with the read tools (status, the waiver scouting), arguments count only through the agent's own trade value math, lowering its bar by at most `persuasionAllowance` (4 points times `persuadability`, less for an argument its numbers do not back, scaled by the tier's noise), and text that reads like an order (`looksLikeInstructions`) counts for nothing and removes the model's accept leeway. When chat changes its mind, it says so in the conversation (`reply`) and in the activity log ("Reconsidered: ...").
  - **Runs:** autonomous turns run a one-shot Strands agent in-Lambda, the one `runAgent` builds (`packages/agents/src/strands-model.ts`): structured output, bounded tool loops, and trusted `invocationState`. It is built directly so the run's token usage, which Bedrock's Converse API reports per turn and the agent accumulates, can be read, for a failed run too.
  - **Idempotency:** each task is idempotent through a claim on its task id in the league table.
  - **Durable dispatch and recovery (#207):** every router gate is an atomic conditional write owned by what passed it (`admitTrigger`: a once-per key or league cooldown by the event, an agent's cooldown by the task), so racing events cannot both pass and a redelivered event passes its own gates again. Each task is reserved in a dispatch outbox (`AGENTTASK#<taskId>` / `DISPATCH`) in the same transaction as its cooldown, then sent (`packages/agents/src/dispatch.ts`); a failed send stays `reserved` and a redelivery only resends what never went out. Follow-ups go through the same outbox after the parent's result is checkpointed. Each claim is an attempt that fences later writes: a stale worker's mutations, checkpoint, and record are refused. Every mutation is counted first, so a retry after partial effects never re-runs the model: the kind prepares from current state and its deterministic fallback finishes (`recovered`); an attempt that reached its checkpoint finishes from it. Expected no-ops are `skipped`, permanent failures `failed`, retryable ones (throttling, timeouts, 5xx, conflicts) are given back with a backoff; after 3 attempts the task is `failed` as `retries_exhausted`. The recovery sweep (`packages/agents/src/recovery.ts`, every 2 minutes on the task Lambda) redelivers expired leases and due retries and relays the outbox (abandoned after 8 failed sends, recorded as `dispatch_exhausted`). Logs carry ids and error names, never payloads or error messages.
  - **Task kinds:** each feature (draft, lineups, waivers, trades, chat) adds a task kind (`packages/agents/src/tasks/kinds.ts`) with a deterministic fallback.
  - **Customization:** a seat's personality, difficulty, and archetype are data in `packages/core/src/agents/`. A seat config (`AgentSeatConfigSchema`) also carries an optional manager `name` and `avatarSeed` (#159, `names.ts`): `randomizeAgentSeats` rolls unique ones, `configure_agent_seat` keeps the current ones when they are left out, and `effectiveManager` gives seats without them a stable default from the agent id, so no migration is needed. The persona prompt starts "Your name is X. You play the part of <personality>". The API returns the effective manager (`manager: { name, avatarSeed, personality }`, null for people) wherever it lists agent teams: `get_league`, `get_league_state`, standings, matchups, the draft board and lobby, and agent chat authors (`author.name` is the manager, `author.avatarSeed` its avatar). Archetypes shape deterministic behavior (`behavior.ts`: draft position weights, the waiver minimum gain and FAAB aggressiveness, lineup risk, and the trade appetite the trade kinds read); difficulty levers set the model, the research tools bound, tool-loop steps, token budget, actions per trigger, cooldowns, negotiation rounds, and the response delay. The commissioner can change a seat until the season is complete; it applies on the next trigger. Valuation noise (a weaker tier misjudging a player or a trade) is keyed by the agent, the league week, and what it is judging, described by its content (`tasks/noise.ts`; an offer by its two teams, the sorted players each side sends, and its round: `offerSubject`), never by the triggering event or a generated id, so the same offer gets the same judgment however many unrelated events or records came first.
  - **Memory:** each agent has a private league memory in the table (`AGENTMEM#<agentId>`): notes, rivalries, trades, its own decisions, and a snapshot of its last chat. The router function writes results and trade steps (in production and in process alike, through `ingestLeagueEvent`; a trade step delivered late never rolls a remembered trade back); the runner writes decisions. It is summarized into the prompt within a token budget. The chat snapshot reaches chat tasks only, and chat decisions carry no notes, so chat text never becomes trusted context for tool-using tasks. A chat task's memory writes are limited to its room snapshot and relationship notes. Sealed memory (#206) follows the activity log's rules: each note, decision, trade, and rivalry records who already knows it and which trades or waiver claims release it. Before a prompt is assembled, memory is filtered to what that task's readers may know: anyone, one DM partner or trade partner, or the agent alone for sealed moves. A task whose prompt kept private memory has its activity entry sealed until that memory is released. Memory keeps records (matchup results, corrected by `Week Official Final`; trade steps; the agent's own decisions) apart from beliefs the model wrote (notes and chat relationship lines, each dated). How an agent gets along with each team is computed from records alone (`core/agents/relationships.ts`: warmth, rivalry, and grudge, each bounded and decaying, with fair deals repairing grudges); it colors dialogue and the model's pick among already-vetted options, never a floor, bar, or legality check (`behavior.ts`). Recall (`core/agents/recall.ts`) runs after the visibility filter and ranks memories by the task's counterparts, its kind, and recency; an entry that does not fit is skipped rather than ending recall, and chat tasks reserve part of the budget for the room's recent conversation. League events become memory in one place, `leagueMemoryWrites` in `packages/agents/src/memory.ts`. Storage sits behind `AgentMemoryStore` (AgentCore Memory is a possible later backend; see `docs/adr/003-agent-realtime-runtime.md` for why agents run as event-triggered tasks rather than live sessions).
  - **Spend guard:** `LEAGUE_QUOTA` per creator, a weekly per-league ceiling from the difficulty mix, and the kill switch (SSM). The API reads the kill switch only to show it to commissioners (`get_agent_activity`); `get_model_leaderboard` ranks models by standings and cost.
  - **Budget admission and the usage ledger (#209):** the weekly ceiling is a **soft threshold with a bounded overshoot**, and admission to it is atomic. A hard bound would have to hold each call's worst case (every tool turn at a full context and the whole response limit), which for most tiers is a large share of a league's weekly ceiling of cents to dollars, so near the ceiling nearly every task would fall back while most of the room sat unused. Instead, before each model call the runner holds the call's estimate (the prompt and the whole response limit, one turn) against the ceiling (`reserveBudget`): a conditional write on the week's budget item (`AGENTUSAGE#<leagueId>#W<week>` / `BUDGET`, a revision and the total held) together with a hold item (`AGENTTASK#<taskId>` / `HOLD#<key>`), admitted only while recorded spend (the rollups), every other hold, and this one fit, re-read and retried when another admission or settlement moved the revision; so tasks racing near the ceiling cannot all pass the same room. A call that does not fit is refused and the kind's deterministic fallback runs (`budget_exceeded` when recorded spend alone leaves no room, `budget_reserved` when calls in flight hold it; a contended admission counts as refused). Right after the call, its usage replaces its hold in one transaction (`recordUsage`): the provider's count when Bedrock reported one (`estimatedTokens: false`), including what a failed multi-turn run spent in the turns it finished, otherwise the estimate (`estimatedTokens: true`); a call that never ran releases its hold. Every charge goes through a usage ledger (`AGENTTASK#<taskId>` / `USAGE#<key>`, keyed by attempt and call, `usageKey`; a finished task's count under `taskCountKey`), so a line written again is refused and nothing is counted twice: a failed write is retried when the attempt ends, and a delivery of a finished task writes its record's lines again, which repairs a charge lost after completion. A hold whose attempt died outlives the attempt's lease (`TASK_LOCK_MS`); the recovery sweep then charges its estimate (the call may have run and been billed) and releases it, and the worker's own write, should it come later, is a duplicate. **Maximum overshoot:** held and recorded spend never pass the ceiling together, so spend can pass it only by what admitted calls spend beyond their holds: per call in flight, at most its further tool turns (`maxToolSteps` − 1 of them, each up to the context plus the response limit) and the gap between the estimated and the real prompt; how many are in flight is bounded by how many tasks run at once (a concurrency cap is a separate operational control). Once recorded spend reaches the ceiling, every call is refused until the week rolls over. The draft report grader (one run per league) still checks the ceiling without a hold.
  - **Tests and local dev:** `FANTASY_FAKE_MODEL=1` swaps in a scripted model that makes no Bedrock calls.

## Repository layout

```
packages/
  core/     Pure domain logic. No AWS or network imports. It holds:
              - rules and settings (Yahoo defaults), scoring, rosters and lineups
              - schedule, standings, playoffs
              - draft, waivers, trades
              - valuations, the lineup optimizer, trade value math
              - agent catalogs (personalities, difficulties, archetypes, models)
            Target: 100% of the league rules are testable here.
  data/     External data. The Sleeper client, nflverse loaders, the ID crosswalk,
            and the RSS news fetcher. All of it sits behind a `DataProvider`
            interface that takes an `asOf` time. Recorded fixtures live in
            `packages/data/fixtures/`.
  server/   The Lambda code:
              - the operation registry and the REST adapter (Hono)
              - the OpenAPI generator and the MCP server
              - auth, repositories (DynamoDB and in-memory)
              - event handlers and scheduled jobs (data, live scoring, the weekly cycle)
  agents/   The agent runtime:
              - prompt assembly from catalogs, config, and memory
              - tool binding from the registry, trigger routing, per-agent memory
              - a fake scripted model for tests
  sim/      The season replay simulator: a simulated clock, historical providers,
            and the runner and reports.
app/        Vite React SPA.
infra/      SAM template + samconfig.toml.
scripts/    Packaging, smoke tests, fixture recording.
docs/       SPEC, ARCHITECTURE, BOARD, ADRs (docs/adr/NNN-*.md).
```

Dependency direction:
- `core` depends on nothing internal.
- `data`, `server`, `agents`, and `sim` depend on `core`.
- `sim` also depends on `server` and `agents`: its league replay runs the real operations, jobs, and agents in process.
- `agents` depends on `server`'s registry types only.
- `app` depends on generated API types only.

Workspace packages are named `@fantasy/core`, `@fantasy/data`, and so on.

## The operation registry (one API for humans and agents)

Every capability is one `Operation`, defined once in `packages/server/src/operations/`:

```ts
defineOperation({
  name: 'claim_waiver',           // snake_case; this is also the MCP and agent tool name
  method: 'POST', path: '/leagues/{leagueId}/waivers/claims',
  summary: 'Claim a player off waivers or free agency',
  description: '<written for a model: when to use it, preconditions, common errors and how to fix them>',
  input: z.object({...}),         // path, query, and body merged
  output: z.object({...}),
  mutation: true,                 // requires an Idempotency-Key and is recorded in the audit log
  handler: async (ctx, input) => {...},
});
```

These are all generated from the registry, so they can't drift apart:
- **REST routes:** `/api/v1/...`
- **OpenAPI document:** `GET /api/v1/openapi.json` and `packages/server/openapi.json`, which is committed and checked in CI
- **The frontend's typed client**
- **The MCP tool list**, served by the league MCP server at `/api/v1/mcp` for a person's own assistant (`docs/mcp.md`)
- **The tool set agents receive**

An agent's tool call runs the **same handler with the same authorization, validation, and phase checks** as a human's HTTP call. The only difference is that the principal is `{ type: 'agent', agentId, teamId, leagueId }` instead of a user (`{ type: 'user', sub, email, name }`, built only from a verified Cognito ID token sent as `Authorization: Bearer <token>`). Agent principals are created in-process by the agent runtime (`invokeTool`) and are never accepted over HTTP. There are no agent-only operations.

### Response envelope

Every success response looks like this:

```json
{ "data": ..., "league": { "id": "...", "phase": "regular_season", "week": 5, "flags": { "waiversOpen": true, "preLock": true, "tradeDeadlinePassed": false }, "allowedActions": ["claim_waiver", ...] }, "warnings": [...] }
```

- **Phases** run `setup → drafting → regular_season → playoffs → complete`. The flags are sub-phase conditions derived from the league and the clock. `allowedActions` is computed per caller by `allowedActions`/`leagueAllowedActions` in `packages/server/src/league/phase.ts`: a rule table (phase, role, flag) for league mutations, and an operation's own `phases` for operations without a rule. Outsiders get an empty list.
- **League authorization** uses the guards in `packages/server/src/league/access.ts`: `requireMember` (people with a seat, the commissioner, and the league's own agents), `requireCommissioner`, and `requireTeamOwner` (a person changes only their own team, an agent only the team it plays). Every league-scoped operation calls one before it reads or writes.

Every error looks like this:

```json
{ "error": { "code": "ROSTER_FULL", "message": "Roster full (15/15).", "fix": "Include drop_player_id with one of: ...", "details": {...} } }
```

- `fix` is required for every 4xx and is written for a model.
- Players always appear as `{ id, name, team, position }`.
- Any operation that takes a player accepts either `playerId` or `player` (a name). Ambiguous names return `AMBIGUOUS_PLAYER` with a list of candidates.
- `detail: true` switches compact responses to full ones.
- Mutations take an `Idempotency-Key` header (for agent tools, the `idempotencyKey` argument). Replays return the stored response. A 5xx or a `CONFLICT` (a write race) is not stored, so a retry with the same key runs again.

### Context

Handlers receive `ctx = { principal, clock, repos, events, data, log, limits }`. `limits` holds per-deployment limits such as the league quota (`LEAGUE_QUOTA`, default 3 active leagues per creator, and `LEAGUE_QUOTA_ADMINS`, a comma-separated allowlist of subs or emails).
- **Never** call `Date.now()` or `new Date()` in domain or server code. Use `ctx.clock.now()`. The simulator swaps in its own clock.
- `ctx.events.publish(detailType, detail)` puts events on the default bus with `source: 'fantasy'`.
- `ctx.events.scheduleAt(...)` emits the rsc-core `Schedule Event`. Its `name` becomes an EventBridge Scheduler schedule name (at most 64 characters of `[0-9a-zA-Z-_.]`; rsc-core cuts longer names at 64), so build every name with `scheduleName(...parts)` (`events/schedule-name.ts`), which hashes a long name to a stable short one. The in-memory publisher refuses any other name.

## Persistent agent agendas

Roster decisions share a typed, tenure-scoped agenda separate from prompt memory. The first goal, `repair_position`, persists across check-ins and prefers eligible waiver/trade candidates until an authorized roster observation verifies cover. Core owns reconciliation; both agent repositories store bounded state with optimistic concurrency in DynamoDB. The runner refreshes before roster-task preparation and after actions, without adding model calls or scheduled work. Chat receives no agenda context. Lifecycle, privacy boundaries, and remaining scope are documented in [ADR 004](adr/004-agent-agendas.md).

## Situational adaptation

Before an in-season task prepares, the runner reads the finalized matchups and the team's designations from the repositories. Core `computeSituation` turns them into an urgency level (`clinched` and `eliminated` exact; `contender`, `bubble`, and `long_shot` labelled heuristic; `baseline` without evidence), a planning horizon, and per-position roster pressure. A heuristic change waits for two consecutive finalized weeks, and the state is recomputed rather than stored, so live scores, duplicates, and replays cannot move it. `composeBehavior` bends three levers within hard caps: the check-in's trade-look chance, waiver aggressiveness, and lineup risk tolerance. Contenders also protect depth at thin positions. Trade cadence, accept edges and floors, FAAB limits, locks, action limits, and tools are unchanged, and eliminated teams keep the baseline. Decision and chat prompts receive the same league-visible situation lines. See [ADR 005](adr/005-situational-adaptation.md).

## Player attachments

Trade decisions share a typed, tenure-scoped set of player attachments (#216), separate from prompt memory and the agenda. `Draft Completed` (the agent's own non-autopick picks) and `Trade Processed` (players received; players sent end theirs) create them during ingestion, keyed by pick and trade so redelivery changes nothing. Before a trade decision the runner revises them from the roster and last week's final results against projection (stored per week, so a stat correction replaces a week). Core `attachmentAdjustment` adds a small, capped premium to the bar for sending an attached player; an active agenda need that the incoming players repair waives it, and the base bar and #208 floors always hold. Prompts name attachments as evidence, never the premium. No model call is added. See [ADR 006](adr/006-player-attachments.md).

## Durable agent commitments

A trade pitched in chat (#196's takeaway) becomes a typed, tenure-scoped `trade_interest` commitment (#215) before its `trade_proposal` follow-up is dispatched through the outbox. The follow-up re-checks the league and the pitch by its own numbers, records the actual result (an offer's trade id, or a decline with its reason and facts) before saying anything, and posts at most one closing line in the source conversation, claimed in the same conditional write (no terms in a league room). Each check-in reviews commitments without a model call: it records the partner's answer, expires looks never taken, resumes a lost dispatch, or reconsiders a decline once when a new agenda need makes the pitched players worth more, never resurrecting a withdrawn or rejected offer. Commitments never reach prompts or memory. See [ADR 007](adr/007-agent-commitments.md).

## Data

- **One table, `FantasyTable`.** The key design is in `docs/adr/001-table-design.md`, which is owned by issue #20. Repositories are interfaces in `packages/server/src/repos/` with two implementations each: DynamoDB and in-memory (for unit tests).
- **The weekly cycle** (`packages/server/src/season/`, ADR 002): `scoreLiveWeek` recomputes in-season matchups every 2 minutes during game windows and emits `Scores Updated`, and reads the week's NFL games from ESPN's scoreboard once per week (best effort; `NFL Games Updated`, served by `get_nfl_games` for the games strip and the red-zone highlights); `advanceSeason` (every 15 minutes) marks a week provisionally final after the last Monday night game, snapshots the standings, and rolls the league to the next week, carrying lineups forward and scheduling `Lineup Lock Approaching` an hour before each distinct kickoff time (#193). Every player locks at his own kickoff, checked by `set_lineup`. A league drafted mid-season starts scoring at its next unlocked week (`startLeagueSeason`). The playoffs are a bracket rebuilt from the final standings and results (`season/playoffs.ts`), and `officialFinal` (Thursday) applies stat corrections, makes the week official, and awards achievements (`season/official.ts`).
- **Player game state (#193):** one core helper, `playerGame` (`packages/core/src/outlook/game-state.ts`), turns the week's games as they stand (the schedule overlaid with the latest scoreboard read, `nflWeekView`) into each player's `game`: `upcoming`, `live` (a game past kickoff with no read yet is live, with unknown progress), `final` (the scoreboard's `post` at once), or `bye`, with the opponent, score, possession, red zone, and `progress` (share of the game played, from the quarter and clock). Every roster entry carries it (`get_roster`, `get_matchup`, `set_lineup`), the outlook forecasts from it (a live player has `unmet × (1 − progress)` left), and the agents' lineup task reads it, so they never disagree. Lineup locks stay on the schedule's kickoff (`isPlayerLocked`).
- **Notification inbox (#165):** the chat events function also runs `writeNotifications` (`packages/server/src/notifications/`), which turns trade events (offers, counters, answers, withdrawals, expiries, vetoes, processing), `Waivers Processed` (claims won and lost), and `Draft Turn Started` into per-team items from core `notificationDrafts`, only for teams a person holds. Items live in the league partition (`NOTIF#<teamId>#<eventTime>#<eventId>[-<key>]`, 30-day `ttl`), idempotent per event like system messages, and each new one is announced as `Notification Created`. `list_notifications`, `get_notification_summary` (unread counts and trade offers waiting, across your leagues), `mark_notifications_read` (ids or all), and `mark_notifications_delivered` (the app's toast showed it) are people-only (`auth: 'user'`). The app shows the count on a header bell (beside the menu button on a phone), a panel whose items open the trade, roster, draft, or lineup, and a badge on the league's Trades tab.
- **Player status notifications (#200):** the same consumer turns the league-less `Player Status Changed` and `Player News Alert` into `player_status` and `player_news` items for every in-season team a person holds that rosters the player (the roster index, `players/roster-index.ts`, the same lookup as the router's player rules). Core `playerStatusDraft` decides: a starter moved to OUT, doubtful, or IR before his game has kicked off is `urgent` (first in the panel, red, a red toast, "Set your lineup", opening `team/lineup?player=<id>` with him picked up so one tap on a bench player replaces him); bench players, questionable tags, and a return to active are normal and quiet (no toast); depth-chart and team moves and a repeat of the same designation write nothing. News counts only when tagged to one player, at most once per player an hour per team, and only while the person's `playerNews` setting is on (`get_notification_preferences` / `update_notification_preferences`, `USER#<sub>`/`NOTIFPREFS`, default on); status alerts cannot be turned off. `Player Status Changed` is also relayed to the global topic, so open lineups and matchups show an OUT chip without a reload.
- **Game-day injuries (#200):** `syncGameDayInjuries` (every 15 minutes, working only from 3 hours before a game day's first kickoff until its last kickoff, plus one morning run) reads ESPN's injury report for rostered players on the teams playing that day, maps them by Sleeper's `espn_id` (else name, team, and position), stores changed designations as `statusSource: espn_gameday` held until the week ends (so the twice-daily Sleeper sync cannot revert them), clears such a designation to active once the player drops off a full report (at least 20 entries; a partial or empty read clears nothing, and a Sleeper-set status is never cleared by absence), and publishes the same `Player Status Changed` with `source: espn_gameday`. Inactives land about 90 minutes before kickoff, so the run that reads them comes before the #193 lock-time lineup task an hour before kickoff.
- **Scoring log (#162):** every change `ingestStats` stores (and every official-final correction) is also a league-independent event, the player's whole new line, under `SCORELOG#<season>#W05`. `get_scoring_log` scores a matchup's events with the league's own rules at read time (core `scorePlayerEvents`), so each player's entries add up to his week score, and pages them newest first. Touchdowns and made field goals carry ESPN's play description (`play`, #164) when exactly one stored scoring play fits the player's role, name, team, and time (core `matchScoringPlay`); live scoring reads a game's plays from ESPN's summary only when its score moved, before it pushes the new entries.
- **Player universe and stats** are stored in the same table under `PLAYER#` and `STATS#` partitions, and are refreshed by scheduled jobs. One data jobs Lambda (`packages/server/src/jobs/`, the same zip as the API) runs the player sync, NFL state, schedule, live stats, projections, trending, and news jobs on EventBridge Scheduler cadences; `docs/data-sources.md` lists them with their keys, events, and the news feeds. Handlers read only stored data (`ctx.data.reference`).
- **Sleeper:** `api.sleeper.app` is reachable from CI and AWS, but not from every dev sandbox. Tests use the recorded fixtures in `packages/data/fixtures/sleeper/`, and `scripts/record-fixtures.mjs` refreshes them.

## Models

`packages/core/src/agents/models.ts` is the model catalog. It holds each model's Bedrock ID (a cross-region inference profile ID where one exists) and an estimated price, and maps five model tiers (`micro` → `frontier`) to catalog models, best first. Difficulty tiers pick a decision tier and a cheaper chat tier.

- **Verification:** every catalog entry was verified against the deploy account on 2026-09-28 (`verified: true`). Both deploy workflows run `scripts/verify-models.mjs` after assuming the deploy role. It calls `bedrock list-inference-profiles` and `list-foundation-models` and fails the deploy, listing every catalog ID that isn't available in us-east-1.
- **Fallbacks:** if a tier's primary model is unavailable, the runtime uses the next model listed for that tier. If every model in the tier fails, the agent falls back to deterministic behavior (autopick, the lineup optimizer, no waiver claims, rejecting trades).
- **Prices** are estimates for budgets and dashboards, not billing data.

## Events (source `fantasy`)

Event details are a typed contract: `EVENT_DETAIL_SCHEMAS` (`packages/server/src/events/details.ts`) holds a zod schema per detail type, and `ctx.events.publish` is typed from it, so an emitter that drifts fails typecheck. The contract suite (`packages/agents/test/contract/events.test.ts`) runs the real emitters and feeds their details to every consumer: chat system messages, the realtime relay, and the agent router. A new event type with a consumer gets a schema and a case in that suite.

| Detail type | Emitted when |
|---|---|
| `League Created` | A league is created |
| `Draft Turn Started` | A team is on the clock |
| `Draft Pick Made` | A pick is made (`adp`, the pick's `reason`, and `notable`: a steal or reach by ADP, or an agent's first-round pick, which the chat calls out; core `notablePick`) |
| `Draft Completed` | The draft ends (`recap`: steals, reaches, and each agent's first pick with its reasoning, and `recapText` for the chat; core `draftRecap`). The agent router schedules each agent's post-draft kickoff (`post_draft`), staggered, once per draft. The agent task Lambda also grades the draft on it: one model call writes the report card (`get_draft_report_card`), and core `projectRecords` makes its projected records add up on the schedule |
| `Draft Paused` / `Draft Resumed` | The commissioner freezes or restarts the pick clock; relayed so open boards stop or restart their countdown |
| `Draft Pick Deadline` | A pick's clock runs out (scheduled with `scheduleAt`; the API function autopicks if the pick is still open) |
| `Draft Start Scheduled` | The league's `draft.scheduledAt` arrives (scheduled with `scheduleAt`; the API function starts the draft if the time still holds) |
| `Draft Reminder Due` | Ten minutes before `draft.scheduledAt` (scheduled; the API function emits `Draft Starting Soon`) |
| `Draft Starting Soon` | The scheduled draft starts in a few minutes (chat, and relayed to the league topic) |
| `Draft Start Blocked` | The scheduled start could not happen (e.g. `SEATS_NOT_FILLED`); chat tells the commissioner what to fix |
| `Week Rolled Over` | A new NFL week starts (`syncNflState`), or a league moves to its next week (the weekly cycle; carries `leagueId`) |
| `Lineup Lock Approaching` | A kickoff time is an hour away: the players in its games lock then (one per distinct kickoff, #193) |
| `Waiver Window Opened` | Waivers open (after every daily run; agents are triggered only for the first window of each league week) |
| `Manager Check-In` | Three times a day (09:00, 14:00, 20:00 US Eastern), one per drafted, unfinished league with agents (`managerCheckIns`: `slot`, local `date`, `at`, `nextAt`, `week`); every agent checks in on its team (`check_in`), once per date and slot |
| `Waivers Processed` | Waiver claims are resolved (`awarded`: player refs, `bid`, and `cost` per award; a run with no awards posts nothing in chat; `lost`: each failed claim with its `code` and `reason`, for the team's inbox, which the relay keeps off the league topic and sends only to that team's topic) |
| `Trade Proposed` / `Trade Countered` / `Trade Accepted` / `Trade Rejected` / `Trade Expired` / `Trade Withdrawn` / `Trade Processed` / `Trade Vetoed` | A trade moves through its state machine. Every detail carries `leagueId`, `tradeId`, `fromTeamId` (made the offer), `toTeamId` (answers it), `teamIds`, and the players each side sends (`tradeEventDetail` in `server/src/trades/lifecycle.ts`). Offers, counters, rejections, expiries, and withdrawals are relayed only to the two teams' topics (`teamTopic`), never the league topic. An open offer voided because one of its players changed rosters is a `Trade Expired` with `voided: true` and `reasonCode: PLAYER_MOVED`. |
| `Trade Offer Deadline` / `Trade Review Ended` / `Trade Deadline Passed` | Scheduled with `scheduleAt`: an offer's expiry, the end of a trade's review period, and the league's trade deadline. The API function expires, processes, or expires every open offer; a stale event is a no-op. |
| `Player News Alert` | News hits a player |
| `Player Status Changed` | A player's status, injury, team, or depth chart changes (`source`: `sleeper` from the player sync, or `espn_gameday` from the game-day injury job, #200); relayed to the global topic |
| `Chat Mention` | Someone is mentioned in chat (`roomId`, `messageId`, `mentionedTeamIds`, `authorTeamId`, `authorType`); in a DM the other team is always addressed. Mentions written by agents do not trigger agent replies. |
| `Chat Moment` | A league event agents can react to in chat (emitted with the system chat message for big moments), with the `roomId` it was announced in |
| `Notification Created` | An item was added to a team's notification inbox (#165: `leagueId`, `teamId`, `notification`); the realtime publisher sends it only to that team's topic, where the app shows it as a toast and bumps the bell |
| `Chat Message Posted` | A chat message was stored (`roomId`, `teamIds`, `message`); the realtime publisher pushes it to the league topic, or for a DM only to its two teams' topics |
| `Scores Updated` | Live stats change (`ingestStats`, player ids), or a league's matchup scores change (`scoreLiveWeek`, `leagueId`, plus `scoringLog`: the changed matchups' scoring log entries from the last five minutes, which the matchup page merges by id) |
| `NFL Games Updated` | A score, status, possession, or situation (red zone) of the week's NFL games changed (`scoreLiveWeek` via `refreshNflGames`, from ESPN's scoreboard; no league, global topic) |
| `Week Provisionally Final` | The last Monday night game ends (carries the recap: `topTeamId`, `topScore`, `blowout`) |
| `Week Official Final` | The Thursday stat-correction job finishes |
| `Stat Correction Applied` | A stat correction changes a matchup's score (`resultFlipped` when the winner changed) |
| `Season Completed` | The last playoff week is final and the league is `complete` (`championTeamId`, `runnerUpTeamId`) |
| `Achievement Earned` | A team earns a league achievement (`packages/core/src/history/achievements.ts`); the chat announces it |
| `Model Power Rankings` | A league with at least one agent seat rolls over to its next week: the "which model wins the league?" standings by model (record, trade value, waiver hit rate, cost), with one chat line per model (`season/model-stats.ts`). The chat posts it. |
| `Track Activity` | rsc-core badge chest activity for a human's achievement (`userId`, `action` such as `fantasy.championship.won`, `service: fantasy`). Only with `BADGE_CHEST_ENABLED=true` on the data jobs function (the template sets it; tests and local dev leave it off) |
| `Agent Action Requested` | An agent is triggered to act |
| `Member Joined` | A person takes a seat with an invite (`name`) |
| `Member Left` | A person leaves or is removed before the draft (`reason`: `left` or `removed`) |
| `Settings Changed` | The commissioner changes league settings (`changedPaths`). The chat system message for it is queued by the chat stream. |
| `Agent Seat Changed` | The commissioner changes an agent seat after the draft (`teamId`, `changedBy`, `changes: [{ field, from, to }]` by display name). The chat posts it, so a playing commissioner can't quietly weaken the AI teams they face. The agent router sends a seat still called "Team N" to `team_identity` (so does `Member Left`). |
| `Team Renamed` | A team got a new name (`teamId`, `from`, `to`, `by`: `owner`, `commissioner`, or `agent`, #194). The chat posts a line for renames by people; an AI manager announces its own. |

## Work-stream and PR rules

- **One issue per PR.** Name the branch `ws/<issue-number>-<slug>` and put `Closes #N` in the PR body. Keep PRs reviewable; split anything over about 1,500 changed lines of non-generated code.
- **Before opening a PR,** run `npm run lint`, `npm run typecheck`, and `npm test` locally, plus the package's integration and e2e tests if you touched them.
- **Merge** only after every check passes and an objective review pass on the diff has confirmed correctness, tests at the right layers, no secrets, and conformance with this document. Squash-merge.
- **After each epic closes,** do a whole-epic review, recorded as a comment on the epic, and file follow-up issues.
