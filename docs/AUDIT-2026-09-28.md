# Bug and quality audit — 2026-09-28

The architecture is in good shape, but I would prioritize a reliability pass before adding more features. The most serious problems are in concurrent roster mutations and recovery after partially completed workflows. High coverage currently misses these cases.

This was a broad source and test audit of current main plus all five open PRs, not an exhaustive proof of correctness. The audit itself made no application fixes, GitHub comments, merges, or deployments. Line references below are to the audited revision and may have moved.

## Scope and evidence

Baseline: `main` at `3d9bbc8ca26d55e315d18d33ad9bd7aa42d03658`. Reviewed domain rules, API authorization and idempotency, DynamoDB repositories, draft and season workflows, waivers, agent execution and activity privacy, chat/realtime, frontend state handling, infrastructure, and CI. Open PR review covered their changed source, relevant tests, descriptions, CI status, and merge relationships. Full test suites were run on main; the PR suites were not all rerun locally.

Five new regression tests reproduce product bugs: four against main and one against the exact queue hook from PR #141. They intentionally assert the correct behavior and fail. The two concurrency cases use authenticated HTTP requests and the DynamoDB implementation through dynalite; promises control the interleaving without sleeps.

## Findings, in priority order

### 1. P1 — Two teams can acquire the same free agent

[Ownership acquisition](../packages/server/src/waivers/rosters.ts)

The code treats an ownership lock as stale whenever its holder's roster does not yet contain the player. That is also the normal interval between acquiring the lock and saving the roster. Team B can reclaim team A's live lock during that interval, after which both roster writes succeed.

Reproduction: pause Alice after her player lock is acquired but before her team write; let Bob claim the same player; resume Alice. Both requests return 200 and both rosters contain Bijan Robinson. The final lock identifies only one of the two owners.

Fix direction: atomically commit ownership and the roster change, or introduce a reservation protocol that distinguishes an active acquisition from an abandoned lock. Checking the current roster alone cannot distinguish them.

### 2. P1 — Concurrent pickups bypass the roster limit

[Conflict retry](../packages/server/src/waivers/rosters.ts)

The claim handler validates capacity before calling `changeRoster`. When the team version changes, `changeRoster` reads the latest roster and retries its write without revalidating capacity. The retry protects existing entries from being overwritten but does not preserve roster legality.

Reproduction: a three-slot roster has two players. Hold one pickup at the roster write and complete another pickup first. Resume the first request. Both return 200 and the final roster has four players.

Fix direction: rerun capacity, position, and acquisition-limit validation against the fresh state, and make those checks part of the same concurrency boundary as the mutation.

### 3. P1 — A transient failure can strand draft startup

[Draft phase transition](../packages/server/src/operations/draft/start-draft.ts)

The league moves to `drafting` before schedule creation, agent-seat setup, and `announceTurn` finish. If publishing the first turn fails, the request returns 500 after the phase changed. Retrying the identical request returns 409 because `start_draft` only permits `setup`. In the reproduced case, neither the first turn event nor its deadline is scheduled.

This is distinct from the existing recovery for a draft item written before the league phase changes. Failures after the phase changes are not covered.

Fix direction: persist startup progress and resume missing steps on retry, or use durable event delivery with a recovery worker. Add a failure test at each boundary, including scheduling.

### 4. P1 — Weekly rollover can permanently lose follow-up work

[Rollover commit and subsequent work](../packages/server/src/season/cycle.ts)

The week change is committed before priority reset, rollover events, model rankings, and next-week lineup-lock timers. If a later step fails, the job retry reads the new week and returns `week_in_progress`; it never finishes the previous rollover.

Reproduction: fail the first event publication after the week update. The league advances from week 1 to week 2, but a retry never emits `Week Rolled Over`. The subsequent lineup-lock scheduling is also skipped. Agents can miss the triggers that prepare their next lineups. The season-completion branch has a similar ordering concern.

Fix direction: record pending follow-up work durably and retry it independently of the current league week. An outbox or explicit workflow-progress record is a good fit.

### 5. P2 — PR #141 can overwrite a saved queue before it finishes loading

[PR #141 queue hook](https://github.com/allenheltondev/ai-fantasy-league/blob/f4e85f23b6cc4d121706a8feb03170b3496cbe23/app/src/draft/queue.ts#L96)

The hook starts with an empty local queue and exposes editing immediately. Although it returns `ready`, the page does not use it to disable Queue, and the hook itself accepts edits while loading. An early click sends a replacement PUT containing only the newly added player. When the older GET completes, it also replaces the displayed queue with stale data.

Reproduction: server queue contains “Saved player”; hold GET; queue “Added player”; finish GET. The server loses the saved entry and the screen disagrees with the server.

Fix direction: gate edits until a successful load, or buffer and reconcile edits with that load. Reset loading/state on league changes and do not treat a failed load as permission to overwrite an unknown queue.

### 6. P2 — Stacked PRs bypass CI

[Checks workflow](../.github/workflows/checks.yaml)

Checks only run for pull requests whose base is `main`. PR #143 targets the research backend branch and #145 targets the queue branch; both have empty check lists. Their parent PR's green checks do not validate their additional changes.

Fix direction: run lint, typecheck, tests, and suitable validation for every PR base. Keep staging deployment restrictions separate from the validation trigger.

### 7. P2 — The documented tooling is not portable to this Windows workspace

[Server scripts](../packages/server/package.json), [infrastructure test](../packages/agents/test/infra.test.ts), [archive path test](../packages/sim/src/replay/human.test.ts)

Six baseline test failures come from CRLF-sensitive comparisons or regular expressions. Normalizing `infra/template.yaml` and committed `openapi.json` to LF makes all six pass without semantic changes. Another test expects `/base/a` instead of the platform's resolved path. The default E2E command cannot start its backend because `FANTASY_LOCAL_AUTH=1 tsx ...` is not valid in Windows cmd.

Fix direction: define repository line endings with `.gitattributes`, normalize text where appropriate, use platform-aware path assertions, and make environment-variable setup cross-platform. The lockfile also contains dependencies whose supported Node range is narrower than the root's `>=22` declaration; the installed Node 24.11 reports engine warnings.

## Additional PR concern needing data validation

[PR #142 projection refresh](https://github.com/allenheltondev/ai-fantasy-league/blob/3094e2ecd28fc9fe583172e622b003c31a35b374/packages/server/src/jobs/sync-season-research.ts#L76)

Once any projection metadata exists in the regular season, refresh stops regardless of how many weeks were fetched. The fetcher accepts partial weekly data, and the existing test explicitly stores only a subset. A first pull containing only one or several weeks can therefore remain frozen and be displayed as a season projection.

The skip behavior is clear from source; I did not verify live Sleeper coverage or reproduce the full ingestion job locally. Before relying on this field, distinguish complete season projections from partial data, show coverage, and decide how incomplete snapshots get refreshed. Green fixture tests do not establish that the provider supplies all future weeks.

## Validation results and limits

- Main lint, typecheck, production build, and all 15 script tests passed.
- Initial workspace coverage run: **2,096 passed, 7 failed, 4 skipped**. Failures are the Windows issues above, separate from the new audit tests.
- After LF normalization, the affected server and agent files passed **22 targeted tests**, including the six formerly failing cases. The POSIX-path assertion was not changed.
- Core: 445 passing tests; 99.62% line / 97.11% branch coverage. App: 287 passing tests; 99.73% line / 98.30% branch coverage. These are strong signals for covered paths, not evidence that concurrent operations or interrupted workflows are safe.
- Four new backend reproductions fail on main; the queue reproduction fails against the copied PR #141 source and was also run using Node 22.23.3.
- E2E first failed on Windows shell syntax. A process-local Git Bash override started the servers, but Playwright's required Chromium revision was absent. Its download then failed with a timeout. **No local browser E2E result is claimed.**
- The production build emits a large-chunk warning: the lazy SDK chunk is approximately 1.54 MB minified / 197 KB gzip. Measure browser cost before prioritizing changes; this is below the correctness issues.
- No live AWS, Bedrock, Momento, or Sleeper behavior was exercised. CI deployment logs were inspected; no production data was modified.

## Recommended sequence

1. Make ownership plus roster updates atomic, and preserve legality on retries. Keep the two controlled-interleaving tests.
2. Make draft startup and season rollover resumable after every write/event boundary.
3. Fix queue loading, enable checks for stacked PRs, and validate the integrated queue/lobby/research UI.
4. Address projection completeness, finish the chat-room rollout, and clean up Windows tooling.

The biggest quality improvement is targeted concurrency and failure-injection coverage. More happy-path tests or a higher line-coverage target would not catch the reproduced failures.
